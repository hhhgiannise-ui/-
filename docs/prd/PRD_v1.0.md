## 1. 项目概述

### 1.1 背景与问题

多人一起旅行、聚餐后，费用分摊长期依赖"群里对账 + 口头转账"：

- 谁垫付了什么、谁还欠谁多少，全靠记忆，**容易漏记、算错**；
- 每次都要凑人数、掏计算器，**不好意思开口要钱**；
- 现有记账软件多为**个人记账**，缺少"多人协作 + 智能分摊"的场景。

### 1.2 产品定位

面向**小圈子（家人/朋友）**的轻量费用分摊微信小程序。

### 1.3 目标用户

- 一起出行、聚餐的家人与朋友小团体（3 ~ 20 人）；
- 核心场景：旅行中随手记账，结束后自动算清、一键转账。

### 1.4 核心价值

> 记账 3 秒，算账 0 秒——**再也不用在群里对账**。

### 1.5 名词解释

| 名词 | 含义 |
|---|---|
| 旅行 Trip | 一次分摊活动的容器，含名称、日期、邀请码 |
| 成员 Member | 加入某次旅行的用户（通过微信 openid 标识） |
| 账单 Expense | 一笔支出：金额、分类、付款人、分摊方式、凭证图片 |
| 分摊 Share | 账单金额在成员间的分配结果 |
| 结算 Settlement | 旅行结束后生成的"谁转给谁多少钱"清单 |

## 2. 用户故事

- 作为**组织者**，我想创建一次旅行并生成邀请码，以便拉朋友加入。
- 作为**成员**，我想用微信一键登录并输入邀请码加入，以便无需注册账号。
- 作为**成员**，我想随手记一笔支出（金额/分类/付款人/分摊范围），以便不遗漏任何一笔。
- 作为**成员**，我想查看全部账单与实时分摊结果，以便知道谁欠谁多少。
- 作为**组织者**，我想结束旅行并生成结算清单，以便大家按清单转账清账。

## 4. 业务规则

### 4.1 数据隔离与权限

- 所有业务数据按 `tripId` 隔离，**仅旅行成员可读写**；
- 删除/编辑账单：仅**记账人本人或管理员**；
- 修改旅行信息、移除成员：仅**管理员**（创建者）；
- 以上规则由**云函数强制校验**，数据库安全规则兜底，前端不做安全边界。

### 4.2 分摊规则（核心算法）

每笔账单可选三种分摊方式：

| 方式 | 规则 |
|---|---|
| 平摊（人均） | 金额 ÷ 参与人数，每人承担一笔 |
| 指定成员平摊 | 记账时勾选"仅部分成员分摊"，仅对勾选者均摊 |
| 代付抵扣 | 付款人垫付整笔，金额记为付款人应收，其余人各摊一份给付款人 |

### 4.3 结算算法（MVP 版）

1. 每人**净额 = 应收合计 − 应付合计**；
2. 净收入者（应收>应付）只收，净支出者只付；
3. 生成**最小化转账清单**：按金额从大到小贪心撮合（大额优先对冲），减少转账笔数；
4. 校验：所有净额之和恒为 0（尾差记给最大付款人）。

### 4.4 金额规则

- 金额以**「分」为单位的整数**存储（避免浮点误差），展示时转元；
- 分摊结果四舍五入到分，尾差记给付款人。

### 4.5 状态机

```
旅行: 进行中 ──结束──▶ 已结算
账单: 未结算（进行中旅行内）──结束──▶ 已归档（计入结算）
结算: 未生成 ──生成──▶ 已生成（旅行标记已结算，账单只读）
```

## 6. 验收标准

### 6.1 核心流程用例

| 用例 | 操作步骤 | 预期结果 |
|---|---|---|
| 创建并加入 | 建旅行 → 获取邀请码 → 另一账号输入码加入 | 双方互见成员列表 |
| 平摊记账 | A 记 300 元餐饮，平摊给 3 人 | 每人应付 100 元 |
| 指定分摊 | B 代付 90 元门票，仅 A、B 分摊 | A 欠 B 45 元 |
| 结算清账 | 结束旅行 | 生成转账清单，净额合计为 0 |
| 越权访问 | 非成员请求旅行数据 | 拒绝访问 |
| 图片凭证 | 记账附图片 | 列表可见图片，存储可查 |

### 6.2 上线条件（真机预览）

- 上述用例全部通过；
- 真机可完整走通"建团 → 记账 → 算账 → 清账"全流程；
- Git 仓库已推送远程，README/接口文档齐全。
